# NORDOI G0.3 R4Q — Two-authority checkpoint quorum under a compromised repository administrator

**Independent administrative trust: NOT IMPLEMENTED. This is a two-key/two-role adversarial LAB, not a separately governed service.**

## Adversarial question

Can the primary NORDOI GitHub repository administrator publish a formerly valid signed release or a fictitious future release and convince the verifier that it is current, **when a second signer's independently pinned key and current checkpoint remain uncompromised**?

R4P's live GitHub witness branch is under the same repository administrator and therefore **does not** satisfy this assumption by itself. GitHub branch protection may apply to administrators when configured to do so, but it does not create a cryptographic authority governed by an unrelated owner. Consequently R4Q cannot legitimately claim to create a second real administrator without the separate administrator's explicit participation and controlled custody.

## Bounded two-key experiment

Native Mac fixture creates **five ephemeral Ed25519 identities** using `/usr/bin/ssh-keygen`: repository publisher A1; proposed successor A2; malicious third publisher; external-witness signer B; forged external-witness signer. A and B private keys reside in different **test directories** and are used through distinct native signing calls. **All keys are still generated and accessible within the same developer-owned test process/account**. This models two roles, not actual administrative separation. No private key is committed.

The verifier retains the original B public key from fixture setup as its **pinned witness authority**. It never accepts a public key supplied by the mutable repository. A publishes a canonically encoded `NORDOI-R4Q-RELEASE-V1` with epoch/sequence and the pinned R4P evidence commit `ff8abe01cc1a527dd84b463dec1736d20a5391a4`, signed with namespace `nordoi-r4q-repository-release@eddarsglobal`.

B separately signs a current `NORDOI-R4Q-EXTERNAL-V1` checkpoint binding exactly the same epoch/sequence/evidence commit **and the specific authorized A public key**, with a different namespace `nordoi-r4q-independent-checkpoint@eddarsglobal`. The verifier rereads the B current checkpoint from the witness fixture at each admission and verifies the SSHSIG against the pinned B key. It then checks both local cursors equal B's current checkpoint, verifies the A signature under the B-endorsed A public key, and requires the requested release equal B's current endorsed version. A signature from A alone, two identical local files or a GitHub branch name are insufficient.

The first Mac test also executes a real `/usr/bin/git ls-remote` against the public R4P evidence branch, requiring its exact pinned head. **This confirms connectivity to an off-device reference but does not make B an off-device service**.

## Required native adversarial trials

1. Actual GitHub evidence branch ref pinned, distinct genuine Ed25519 A/B keys, valid epoch2/seq2 admits.
2. Primary repo administrator A (authentic A signing key) and **both local cursors** revert to epoch1 while B retains epoch2 — denied.
3. Primary repo signer falsely signs epoch3/seq3 while B retains epoch2 — denied.
4. A signer replaced by malicious independently signed identity — denied even when release bytes match B current.
5. Forged external B signer or cross-domain SSHSIG replay — denied.
6. B checkpoint missing/corrupt — fail closed; no fallback to repository-only witness.
7. B-signed endorsement of new A2 publisher key at epoch3 permits A2 but refuses formerly active A1 on the same epoch.
8. Local cursor disagreement — denied.
9. **Required residual counterexample:** If the second witness's current signed view is also restored to a previously genuinely signed epoch1 checkpoint, old A1 and both old local cursors can again pass. A true append-only/monotonic externally governed witness is still absent.

A non-macOS portable negative test makes no native SSHSIG, remote-checkpoint or independent-admin security claim. A separate reference-model control keeps `ResourceEffect::ExternalIo` default-denied, so the GitHub access belongs only to the isolated research test.

## Severe limitations, non-authorization

**No distinct owner or administrative authority is present.** B's signing key is generated by the same Mac/CI test process and its "current" checkpoint is a writable local file in another fixture directory. This is NOT independent custody, a third-party timestamp service, multiple organizations, unforgeable witness freshness, hardware monotonicity or a production quorum. The counterexample explicitly proves that old B signatures may replay if B's current view is compromised. A compromised verifier binary, owner account, GitHub administrator with code deployment authority, compromised B key, B storage rollback or coordinated dual-key takeover defeats the research model.

A genuine administratively separated R4Q acceptance gate would require a real unrelated account/organization, independently controlled signing and endpoint custody, externally approved root public key enrollment, authenticated freshness/monotonicity, revocation and rotation protocols, and measured protection against the primary administrator changing the verifier. **Do not claim PASS for that deployment requirement merely because the simulated tests pass.**
