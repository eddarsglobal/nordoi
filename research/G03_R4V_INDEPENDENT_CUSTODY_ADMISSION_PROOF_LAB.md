## 3. Independent-custody requirements and fail-closed gates

The prototype's `lab_custody_gate` checks the following failures in strict order:

1. `ADMINISTRATIVE_CONTROLLER_NOT_DISTINCT`: Guardian, publisher and observer may be different *keys*, *processes* or *branches*, but must not be under the same authenticated administrative controller.
2. `INDEPENDENT_OPERATOR_NOT_ATTESTED`: An independent accountable operator must be externally verified. Arbitrary identifiers and JSON-provided organization names do not establish operator identity or authority.
3. `OWNER_TRUST_ROOT_NOT_OUT_OF_BAND`: Owner enrollment of the actual guardian public root must have an independently verified fingerprint and authentic out-of-band decision, not merely one generated by the same app/process.
4. `REMOTE_MONOTONIC_HEAD_NOT_ATTESTED`: A dynamic protected append-only state or independently anchored monotonic high-water must be externally attested and survive restoring BOTH local verifier state and older authentically signed receipts.
5. `VERIFIER_INSTALL_NOT_PROTECTED`: The primary GitHub administrator must not be able to replace the production verifier or its root pin without independent detection.
6. `RECOVERY_GOVERNANCE_UNVERIFIED`: Revocation, key rotation, unavailable guardian, lost credentials, split brain, timeout, replay and recovery decisions must be explicitly authorized, logged and externally reviewable.
7. Even if a candidate simply asserts **all six controls are satisfied**, the test-only API returns `EXTERNAL_CUSTODY_PROVENANCE_UNAVAILABLE_IN_RESEARCH`. A Boolean claim is not a verifiable signed external authorization. **There is no positive production admission path in R4V.**

These fields are **adversarial self-claims used to exercise precise rejection reasons**; they are not accepted independent-operator evidence. A future external authorized guardian will require a separate provenance-verification implementation and independent key custody, not setting these fields to `true`.
